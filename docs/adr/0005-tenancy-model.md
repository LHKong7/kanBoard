# ADR-0005 · 多租户隔离：共享库 + tenant 列 + RLS

| 项 | 值 |

| 状态 | Accepted |

| 解决问题 | Q-A6 |
| 依赖 | [ADR-0002](0002-unified-resource-model.md), [ADR-0004](0004-go-server-stack.md) |

## 背景

"多租户隔离"要回答的是：**这套系统会被多少个互不信任的组织同时使用？**

- 只给一家公司内部用 → 部门/团队之间的隔离用 `Workspace` 就够了，`Tenant` 是多余的
- 将来要作为 SaaS 卖给多家公司 → 必须有 `Tenant` 层，且 A 公司绝不能看到 B 公司的任何数据

关键约束：**这个决定必须在 M0 做**。
`tenant` 是否存在于主键与索引中，是数据模型的根基；事后补加意味着全表重建、全部查询重写、
全部权限规则回炉——代价远高于一开始就带上。

而产品路径本身尚未确定（Q-P1：先内部自用还是直接商业化），
因此需要一个「现在几乎不花成本、将来不用重构」的方案。

## 决策

**共享数据库 + 每行携带 `tenant` 列 + PostgreSQL Row Level Security（RLS）强制过滤。**

具体：

1. **所有 Resource 表自始携带 `tenant` 列**，参与主要索引的前缀。
2. **RLS 在数据库层强制过滤**：连接建立时设置 `SET LOCAL app.tenant_id`，
   策略保证任何查询都无法读到其他租户的行——**即使应用层代码写错也不会泄漏**。
3. **应用层不依赖手工拼 `WHERE tenant = ?`**：那是会被遗忘的防线，RLS 是不会被遗忘的防线。
4. **v1 以单租户模式运行**：`tenant` 恒为 `default`。功能上等同于单租户系统，
   用户界面不出现租户概念，运维不增加负担。
5. **Workspace 承担日常隔离**：团队、项目、权限边界都落在 Workspace 上，这是用户真正感知的层。
6. **大客户逃生舱**：未来若有客户要求物理隔离，支持将单个租户迁移到独立数据库实例，
   应用代码不变（连接路由按 tenant 解析）。

### 隔离层级的职责划分

| 层 | 隔离什么 | 什么时候用 |
| --- | --- | --- |
| `Tenant` | 互不信任的组织之间 | SaaS 多客户；v1 恒为 default |
| `Workspace` | 同一组织内的团队/业务线 | **日常使用的主要边界** |
| `Project` | 工作内容 | 项目级可见性 |
| Resource 级 Policy | 单个对象 | 敏感需求、受限文档 |

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| A. 不做 Tenant，只有 Workspace | 最简单 | 将来要 SaaS 时需重建全部表与索引 | 代价推迟但会翻倍 |
| B. 库级隔离（每租户一个数据库） | 隔离最强，合规最好交代 | 迁移、升级、跨租户运维成本随租户数线性增长；小客户成本不经济 | 早期租户少时纯粹是负担；保留为大客户逃生舱 |
| C. Schema 级隔离（每租户一个 schema） | 折中 | 连接池与迁移复杂度高；PG 在 schema 数量大时元数据开销明显 | 复杂度不划算 |
| **D. 共享库 + tenant 列 + RLS** | 现在零成本，将来零重构；数据库层兜底防泄漏 | 需要正确配置 RLS，一次配错影响面大；「吵闹邻居」需靠配额治理 | **已选** |

## 后果

### 正面

- **现在几乎不花成本**：多写一个列、多一条 RLS 策略；v1 用户完全感知不到
- **将来不用重构**：产品走向 SaaS 时，打开租户注册即可，数据模型不动
- **数据库层兜底**：应用层漏掉租户过滤也不会泄漏——这是比代码审查更可靠的防线
- 与 ADR-0002 的统一 Resource 模型天然契合：`tenant` 是公共头部字段之一

### 负面 / 代价

- RLS 配置必须正确，且每张新表都要记得启用——需要迁移脚本模板与 CI 检查兜底
- RLS 对查询计划有轻微影响，复杂查询需要验证索引仍被使用
- 共享库存在「吵闹邻居」风险：单个租户的重负载影响他人——靠连接池配额与限流治理
- 合规要求物理隔离的客户仍需走逃生舱路径，届时有一次性迁移成本

### 需要后续处理

- [ ] 迁移脚本模板：新建表自动启用 RLS 并附带策略
- [ ] CI 检查：存在未启用 RLS 的 Resource 表即失败
- [ ] 跨租户查询的白名单机制（仅平台运维，需二次授权 + 审计）
- [ ] 租户级资源配额（连接数、QPS、Agent 预算）
- [ ] 单租户迁移到独立库的操作手册（大客户逃生舱）

## 验证方式

- 自动化测试：以 A 租户身份查询 B 租户对象，全部返回 404/403（FR-IAM-015）
- 故障注入：**故意移除应用层的 tenant 过滤条件**，RLS 仍须阻止跨租户读取——这是本 ADR 的核心验收项
- CI 检查：所有 Resource 表均已启用 RLS
- 压测：RLS 开启前后的查询计划对比，确认索引仍被命中
