## 这份表本身有多可信

统计口径：只算 Must（M）。Should / Could 另计。**Must 的总数（102）
与每模块的条数已经用脚本对着 PRD 核过，是准的**；
`pnpm lint:coverage` 保证合计等于各行之和。

但"已交付"这一列是人写的，而它已经被发现错过三次，
错法完全一样——**把一条 Should 当成缺失的 Must 写进了备注**：

| 行 | 原来写的缺口 | 实际 |
| --- | --- | --- |
| WF | SLA 超时、可视化编辑器 | 这两条是 S 与 C。真正缺的是 FR-WF-006 外部事件触发 |
| RES | FR-RES-010 事件订阅 / Webhook 出站 | 是 S。12 条 Must 全部交付 |
| ARCH | 按 BC 重组目录 | ARCH 的 Must 里没有这一条。缺的是 FR-ARCH-011 可取消 |
| IAM | OIDC、JIT 授权 UI、委派链 | OIDC 不是编号需求；FR-IAM-006 临时授权与 FR-IAM-007 委派交集都已交付 |

这四行的备注是**照着印象写的**，不是照着需求编号核的。
所以：**已逐条核对的只有 WF、RES、ARCH、DASH 四个模块**，
IAM 与 AGT 也已逐条核对完（见下）。剩下三行（AI / CON / ONT）
的数字还没有重新对过编号——不过前两者的缺口是外部依赖，不是记错。核对时确认缺失的两条现在都补上了：
FR-IAM-012 blastRadius（单次 Run 的影响面上限，动手之前判）、
FR-ARCH-011 可取消。

**FR-ARCH-011 只按验收标准算交付，要说清楚边界。**
验收标准原文是「取消进行中的 Run，含 Connector 调用在 5 秒内全部停止」，
这一条有用例锁住：进程关停会打断在途的 Run，把 Run 迁到 Cancelled
也能被另一个进程里的运行时读到，取消之后不再写回、不再重试外部调用。

但需求正文写的是「**任何**超过 1 秒的操作接受 AbortSignal」，
而读路径（列表、图遍历、Automation Rate 的那次 N+1）目前**都不接受信号**，
客户端断开也不会停止查询。这一块没做，别把它当成做了。

核对 DOM 时抓到了这份表最坏的一种错：**代码引用了需求编号，做的却是别的事**。
`STORY_LIFECYCLE` 里写着 "FR-DOM-004"，守的是"有没有拆出任务"，
而 FR-DOM-004 说的是"必须含结构化 Acceptance"——Story 上根本没有这个字段，
本体里也没有 Acceptance 这个类型。一句写错了编号的注释比没有注释更糟：
它让人以为这条需求已经落地，于是不会有人再去看。现在它真的实现了。

写在这里而不是悄悄改掉数字，是因为这份文档唯一的用处就是可信。
一个被改对了但没人知道曾经错过的进度表，下次还会错。

`sla` 曾经是这份表里最典型的一处虚报：它在状态定义里、在类型里、
在 Task 的 `Doing` 上都写着，**但没有任何代码读它**——
一个看起来配置好了、实际什么也不做的字段，比没有这个字段更糟，
因为有人会以为超时会有人管。现在它由 `SlaSweeper` 巡检，
超时会生成通知或升级到值班，每一条都种过缺陷验证会红。

计时用单独的 `status_since` 列而不是 `updated_at`：后者被任何一次编辑刷新，
于是一个停滞三周、昨天被人补了个描述的任务看起来"刚动过"——
而那正好是最该报警的对象。

FR-WF-006 一开始也被记成"需要真实的 GitHub"，那是错的：
**GitHub 是发送方**。它拨这个号没法在这里验证，但接的这一半可以，
而且必须——验签、认出说的是哪个对象、翻译、进 outbox、跑自动化，
整条链没有一步依赖 GitHub 真的存在。用例发的是 GitHub 真实的
`pull_request` webhook 形状，断言的是"PR 合并后 Task 变成 Done"，
也就是验收标准的原文。

翻译层把外部载荷当**不可信输入**：先验签再解析、只带声明过的字段、
原始报文不落库（里面可能有 token 和整棵 diff）。
验签用 `timingSafeEqual`——字符串比较会在第一个不同的字节上返回，
于是签名可以按响应时间一个字节一个字节地试出来。

接 CI 或 Kafka 时加一条来源配置即可，翻译层不需要改。

RES 这一行此前记的是 **11/12，缺「FR-RES-010 事件订阅 / Webhook 出站」**。
和 WF 那行是同一个毛病：FR-RES-010 是 **Should**，不是 Must。
逐条核对之后 12 条 Must 全部有用例。

顺带把 FR-RES-011 从"人工审查"变成了机器做的事。它的验收标准原文是
「端点清单审查通过」，而人工审查有个众所周知的性质：第一次做得很认真，
然后就不做了。`tests/integration/endpoint-inventory.test.ts` 把实际路由树
和一份写死的清单逐条比对——加一条路由就会红，那时必须回答
"人也走这条路吗"。种过一条 `POST /v1/agents/:id/run` 验证它会触发。

FR-AI-001 是这一行里第二次纠正判断。它的验收标准是
「生成对象树并**可逐节点接受/拒绝**」——那是**机制**，不是模型输出质量。
和整个 Agent 运行时一样，用确定性模型就能完整验证（运行时 11/11 就是这么测的）。
把"需要模型才能产出好内容"和"没有模型就做不了也验不了"混为一谈，
是我先前把这一整块记成 ❌ 的原因。

改动本身：Draft 模式不再直接创建目标对象，而是一个节点落一条 `Proposal`。
接受时才真的创建，走的是普通 `create`，所以本体校验、权限、审计、事件一个不少——
**Agent 提议的对象和人建的对象没有区别**，只是多了一步谁来点头。
原先那条"Draft 直接落库"的用例因此红了，那正是这次改动的意义：
只能对整棵树表态的话，实际结果是全都不要。

这一段上一版写的是「其余几条按理也能验证，本轮没排上」。那句话现在兑现了：
002 / 004 / 006 / 007 / 009 / 010 的验收标准全是**可判定的条件**——
覆盖率、依赖与 capacity、证据、出处、时效、负责人——于是它们落成了一组纯函数
（`src/domain/ai/capabilities.ts`）：**模型负责生成候选，这一层负责判定候选合不合格**。
两件事分开之后，"AI 做得对不对"不再是一个只能靠感觉回答的问题。

判定失败时列出的是**具体哪几条不满足**，不是一句"未达标"。
一个只会说未达标的校验，使用者除了重跑一次别无选择。

这一组用变异测试验过：往每条规则里种一个缺陷（门槛降到 50%、
不查依赖顺序、有出处的也打标记、过期的照推……），19 条全部被测试逮到。
第一轮跑出来是 18/19——活下来的那条是 FR-AI-010 把
"留下哪些"和"报告哪些"各写了一遍同一个条件、方向还相反，
于是改坏一处的表现是**清单少一条、同时报告"全都有负责人"**。
判据现在只写一次，用例也补上了对另一半的断言。

剩下 FR-AI-003（估点中位偏差 ≤ 1 档）：这一条要的是模型输出的**准确度**，
不是机制，确实需要真实模型加三个迭代的历史样本。它和上面那六条的区别，
正是"没有模型就做不了"与"没有模型就验不了"的区别。

FR-AI-013 要说清楚主防线在哪：**结构性的那一层**——模型的动作空间是一个
封闭联合（finish / propose / call），能提议什么由 Agent 声明的 `mayPropose`
限死，能调什么工具由连接器白名单限死。注入成功也拿不到新权限。
文本中和是第二层，防的是"检索来的内容冒充系统在说话"：
即使拿不到权限，一段写着 `### system:` 的需求描述也足以让模型误解自己的角色。

（[性能基线](perf-baseline.md)里列表查询 P95 约 20ms），
再大一个量级就需要物化。届时这份指标定义就是物化任务的输入，
不需要重写口径。

Agent 视角凑齐 8 项时给指标模型加了**求和 / 求平均 / 比率**——
数条数答不了"花了多少钱"。加的是动作种类，不是自由度：
仍然只接受属性名，不接受 `sum(cost * 1.2 + fee)` 这类表达式。
一旦允许表达式，指标就不再是"能被读懂、被复算、被质疑"的东西了。

补齐 Project 与 Team 视角时，差的不是代码而是**对象**：
Velocity 要有 Sprint，Milestone / Risk / Budget 各自要有类型。
先建类型再补指标是对的顺序——反过来做只会得到几个恒为零的数字，
而恒为零的指标比没有指标更容易让人误判。这四个类型按 PRD 03 的
关键属性与不变量建出来了，其中 Risk「高风险必须有 owner 与 mitigation」
做成了 `Mitigating` 状态的守卫：登记一条风险不该有门槛，
但声称"正在缓解"就必须说得出对策。

Cycle Time 与 Lead Time 目前只给出**计数**，没给时长分布。
`status_since` 已经在库里（007_sla.sql），把它展开成分布是下一步——
现在的口径写在指标定义里，没有假装它是分布。

**Automation Rate 是唯一的例外，它明显更贵**：每个工作项都要拉一次历史
再算一次编辑距离，是一次 N+1。目前用一条 5,000 项的硬上界兜住，
命中时响应里的 `truncated` 为 true——**少算可以，不声不响地少算不行**。
这一条是已知的、要还的债，不是"没想到"。

## 差得最远的两块

**AI 能力（12 Must，交付 11）。** 这一行改过三次，每次都是同一种误判：
**把"需要模型才能产出好内容"当成了"没有模型就做不了也验不了"。**

边界那四条（开关、出境控制、注入防护、指标物化）根本不涉及模型。
FR-AI-001 的验收标准是"可逐节点接受/拒绝"——那是机制。
002/004/006/007/009/010 的验收标准是覆盖率、依赖与 capacity、证据、
出处、时效、负责人——**全是可判定的条件**，于是它们是纯函数，
用例直接照着验收标准的原文写，再用变异测试确认每条都测到了。

只有 FR-AI-003（估点中位偏差 ≤ 1 档）真正被外部依赖挡住：
它要的是模型输出的准确度本身。**没有凭据时 runner 默认不启动**：
退回到假实现会安静地产出一堆无意义的草稿，而草稿是会被人当真的。

**连接器（12 Must，交付 10）。** 统一契约与网关做完了——授权、审计、幂等、
限流、退避重试、熔断、白名单、人工确认、凭据注入、按分级脱敏，
全部在**唯一入口**上强制执行，每一条都种过缺陷验证会红。
FR-CON-002「无法绕过」用两条 CI 规则挡住（依赖分析 + 源码扫 `fetch`），
两条都验证过会触发。

缺的是具体集成，而**阻塞理由不一样**，不该混作一谈：

| ID | 状态 |
| --- | --- |
| FR-CON-001 统一契约（Read/Write/Observe/Subscribe/Action） | ✅ |
| FR-CON-002 Agent 无法绕过 Connector 直连外部系统 | ✅ 两条 CI 规则（依赖分析 + 源码扫 `fetch`），都验证过会触发 |
| FR-CON-003 每次调用先经 PDP 授权并审计 | ✅ |
| FR-CON-004 写操作幂等 | ✅ 缺幂等键的写直接拒 |
| FR-CON-005 限流、指数退避重试、熔断 | ✅ |
| FR-CON-009 Browser：域名白名单 + 动作范围 + TTL | ✅ 真实 Chromium 端到端验证 |
| FR-CON-010 Browser 敏感动作强制人工确认 | ✅ `submit` 显式标注，未确认时阻断 |
| FR-CON-011 凭据由 Secret Manager 注入，上下文无明文 | ✅ |
| FR-CON-012 数据分级与字段脱敏 | ✅ |
| FR-CON-006 GitHub | ❌ 被外部依赖挡住：需要真实仓库与凭据 |
| FR-CON-007 Jira | ❌ 被外部依赖挡住：需要真实实例，且要双向同步 |
| FR-CON-008 MCP：接入任意 MCP Server 作为 Tool | ✅ stdio JSON-RPC 全程往返，对面是一个真实的本地 server |

这张细分表是逐条列出来才发现的：CON 原本记的是 8，而按编号数是 7
（加上 Browser 那两条才是 9）。和 AI 那一行一样，多出来的那个 1
从来对不上任何编号。`lint:coverage` 现在会比对"某一行 vs 它自己的细分表"，
所以这类漂移当场就红。

把这些一律写成"被外部依赖挡住"是不诚实的——**手边有的东西不算阻塞**。
Browser 就是例子：Chromium 一直在这台机器上，写完之后端到端跑通了，
三条控制（白名单、动作范围、人工确认）各自种过缺陷验证会红。
MCP 也做完了：不引第三方 SDK，自己实现 initialize / tools/list / tools/call
三个方法，对面跑的是一个真实的 stdio server（`tests/fixtures/mcp-server.mjs`）。
用假 transport 的话，分帧、id 匹配、通知跳过、错误映射这几处
恰恰最容易错又完全测不到——把"通知当成回复"种进去之后，
14 条用例红了 8 条。

「接入**任意** MCP Server」这句话的代价要写清楚：server 是别人写的代码，
它的声明来自系统外面。所以每个默认值都倒向保守一侧——
工具不默认可用（白名单之外一个都调不了）、
**不默认只读**（没有显式 `readOnlyHint` 的一律当 action，因而走人工确认）、
返回内容一律按 confidential 脱敏。反过来设的话，
接一个新 server 就等于把它声明的一切直接授权给 Agent。

Browser 连接器落地时顺带抓出三个真问题：
白名单按 `host` 比对而 host 含端口，于是 `api.example.com` 配不上
`https://api.example.com:8443/…`；参数校验排在开浏览器之后，
一次少写 selector 的调用要先花几百毫秒拉起 Chromium 才报错；
以及 `src/` 依赖了一个 devDependency——分层检查当场拦下，
那正是它存在的理由。

契约已经把它们变成薄薄一层：实现 `Connector` 接口，声明操作与白名单即可，
授权、审计、幂等、限流、退避、熔断、脱敏全部由网关提供。
