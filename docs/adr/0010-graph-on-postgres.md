## 背景

ProjectOS 的核心能力之一是沿关系推理：全链路追溯、影响面分析、知识候选子图。
自然的反应是"这需要图数据库"。

但引入独立图库会带来三个具体问题，而不只是"多一个组件"：

1. **双写与一致性**：Resource 在 PG，关系在图库，两边的事务无法统一。
   ADR-0002 好不容易用 outbox 保证了业务写入与事件的原子性，这里会重新打开一个口子。
2. **租户隔离要做两遍**：ADR-0005 的 RLS 兜底只覆盖 PG。图库需要另一套隔离机制，
   而那套机制的强度未必等同——"数据库层兜底"的承诺会被削弱成"其中一个数据库层兜底"。
3. **运维面翻倍**：备份、升级、监控、故障演练，全部乘以二。

而当前的规模假设（PRD 12）：v1.0 目标 3000 万条关系，设计上限 5 亿。
递归 CTE 在前者上是完全可行的。

## 决策

**v1 用 PostgreSQL 递归 CTE 实现图遍历与路径查询，关系存在 `relations` 边表中。**

M0 已实现（`src/infrastructure/relation-repository.pg.ts`）：

| 能力 | 实现 |
| --- | --- |
| 广度优先遍历 | `WITH RECURSIVE` + `visited` 数组防环 |
| 最短路径 | 同上，无向遍历，按深度取第一个命中 |
| 方向控制 | `out` / `in` / `both`，通过 LATERAL 子查询合并 |
| 软删除过滤 | JOIN resources 时排除 `deleted_at IS NOT NULL` |
| 待确认关系 | `confirmed IS DISTINCT FROM false`，被人工否决的边不参与遍历 |

### 防环是必需的，不是防御性编程

需求图里成环是**常态**而非异常：`blockedBy` 链会绕回来，
`relatesTo` 天然双向。不能假设它是 DAG——`visited` 数组是正确性要求。
`tests/integration/graph.test.ts` 里有一条用例专门构造 A→B→C→A 验证这一点。

### 隔离边界

所有图操作收敛在 `RelationRepository` 端口（`src/domain/resource/ports.ts`）之后。
领域层只认这个接口，不知道底下是 CTE 还是别的什么。
换存储时改一个适配器，**API 契约与领域层都不动**（FR-RES-015）。

### 何时重新评估

以下任一条件触发，需要新的 ADR：

| 触发条件 | 阈值 |
| --- | --- |
| 关系规模 | 单租户 > 5000 万条边 |
| 查询延迟 | 深度 5 遍历 P95 > 1s（NFR-PERF-003 的目标是 500ms） |
| 查询形态 | 出现真正需要图算法的场景（社区发现、PageRank 式排序、加权最短路） |

**前两条现在都还没有被测量过**——见下方待办。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| A. Neo4j / 独立图库 | 图算法丰富，深度遍历性能好 | 双写一致性、租户隔离要做两遍、运维面翻倍 | 当前规模用不上，代价立刻付 |
| B. Apache AGE（PG 图扩展） | 同库，享受 PG 事务与 RLS；支持 Cypher | 生态与稳定性不如原生 PG；托管服务普遍不支持；与 RLS 的交互未经验证 | 引入不确定性换语法糖，不划算；可作为将来的第一候选 |
| **C. 递归 CTE + 边表** | 同库同事务，RLS 直接覆盖；零新增运维 | 无图算法；深度遍历性能随边数下降；SQL 可读性差 | **已选** |

## 后果

### 正面

- 关系与资源在同一事务里写入，不存在双写不一致
- 租户隔离由同一套 RLS 覆盖，ADR-0005 的"数据库层兜底"承诺完整成立
- 零新增运维组件
- 关系可以直接参与普通 SQL 查询与 JOIN（如"查所有被阻塞的 Task 及其阻塞源"）

### 负面 / 代价

- **深度遍历的成本随边数增长**，没有图库那样的原生路径索引
- 递归 CTE 的 SQL 可读性差，维护门槛高于 Cypher
- 没有开箱的图算法；真需要时要么自己写，要么迁移
- `visited` 数组随深度线性增长，深度上限（当前 10）不是可以随意放大的参数

### 需要后续处理

- [ ] **补压测**：100 万节点 / 300 万边数据集，验证 NFR-PERF-003（深度 5 遍历 P95 < 500ms）。
      这是 M0 出口标准之一，目前未达成
- [ ] 边表索引效果验证：确认 `relations_out_idx` / `relations_in_idx` 在递归中被命中
- [ ] 评估物化路径（materialized path）作为传递闭包关系（如 `contains`）的加速手段
- [ ] 建立关系规模的监控指标，让触发阈值可被观测而不是靠感觉

## 验证方式

- 功能：`tests/integration/graph.test.ts` 覆盖遍历、深度限制、成环、软删除过滤、最短路径
- 正确性：成环用例证明 `visited` 防护有效
- 性能：**待补**（上方待办第一项）
- 可替换性：`RelationRepository` 端口的存在即证明；将来切换时应无需改动领域层与 API
