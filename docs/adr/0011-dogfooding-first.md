# ADR-0011 · 先内部自用（dogfooding），M3 后再对外

| 项 | 值 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-08-03 |
| 决策者 | 项目负责人 |
| 关联需求 | 影响 M1/M2 交付取舍 |
| 解决问题 | Q-P1 |
| 依赖 | [ADR-0005](0005-tenancy-model.md) |

## 背景

ProjectOS 的核心主张是"让 AI 与人共同参与项目交付"。
这个主张的真伪，只有在**真实项目的真实压力下**才能被检验：
需求会变、估算会错、迭代会延期、故障会来。演示环境里造不出这些。

同时，M0 的出口标准里有一条是"绕过 PDP 的写路径为 0"——
这种约束在自己团队每天使用时会被反复冲撞，问题会很快浮出来；
在演示环境里则可能一年都碰不到。

第三个因素：ProjectOS 自己就是一个软件研发项目。它的需求、架构决策、
任务、知识，正是它自己要管理的对象。**这个项目本身就是它最合适的第一个用户。**

## 决策

**先内部自用。ProjectOS 的开发过程从 M1 起在 ProjectOS 中管理，M3 之后再考虑对外。**

### 阶段安排

| 阶段 | 使用方式 |
| --- | --- |
| M1 | ProjectOS 的需求、Story、Task、ADR 迁入系统；团队每天使用 |
| M2 | 接入我们自己的 GitHub；PR 合并自动推进 Task |
| M3 | 首批 Agent 在真实项目上运行；Automation Rate 是真实数字而非演示数字 |
| M3 后 | 引入 2–3 个外部试点团队，再评估商业化 |

### 对交付取舍的影响

| 项 | 影响 |
| --- | --- |
| **M1 必须有可用 UI** | 自用意味着团队每天要用，只有 API 是用不起来的。UI 从"锦上添花"变成 M1 的必需项 |
| **Jira Connector 优先级下降** | 我们自己不用 Jira。双向同步（FR-CON-007）从 M2 必需降为按试点客户需求触发 |
| **GitHub Connector 优先级上升** | 我们自己的代码在 GitHub，M2 的第一个 Connector |
| **多租户继续保持单租户运行** | 与 ADR-0005 一致，v1 `tenant` 恒为 `default` |
| **Confluence 迁移（Q-D1）后置** | 我们没有存量 Confluence |
| **本文档目录本身** | `docs/` 下的 PRD 与 ADR 是 Knowledge 与 Decision 对象的迁移源 |

### 明确的自我检验标准

自用不是"我们也装了一套"。M1 结束时必须能回答：

- [ ] ProjectOS 的需求是否全部在系统内，而不是在别处的文档里？
- [ ] 最近一个迭代的 Task 是否在系统内流转，而不是事后补录？
- [ ] 是否有人因为"系统里太麻烦"而绕开它用了别的工具？绕开的地方就是产品缺陷

第三条尤其重要：**绕开行为是最诚实的反馈**，比任何满意度调查都准确。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| A. 直接对外商业化 | 早拿收入，早验证市场需求 | 早期产品必然粗糙，第一批客户体验差且难挽回；Jira 迁移等重工作要在核心能力成熟前就做 | 拿未成型的产品换一次性的信任消耗 |
| **B. 先内部自用** | 反馈闭环最短；真实压力检验；迁移成本为零 | 样本量 = 1 个团队，有过拟合风险；延后收入与市场验证 | **已选** |
| C. 并行推进 | 两头都不耽误 | 早期团队分不出两条线的精力 | 现阶段人力不支持 |

## 后果

### 正面

- 反馈闭环以天计而非以季度计
- 真实项目的复杂度（需求变更、依赖阻塞、故障回溯）自动成为测试用例
- 迁移成本为零：没有存量数据要迁，没有并行运行期
- M3 的 Automation Rate 是真实数字——用自己团队的交付去验证 AI 是否真的在承担工作，
  比任何演示都有说服力
- 团队对产品的理解不来自需求文档，来自每天的使用

### 负面 / 代价

- **样本量是 1，过拟合风险实在**。我们团队的工作流不等于所有团队的工作流。
  很容易把"我们习惯这样"固化成产品假设而不自知
- 延后收入与市场验证；如果核心主张本身不成立，会晚很久才发现
- 自己是唯一用户时，容易容忍本该修掉的粗糙——因为"我们知道怎么绕过去"
- 缺少外部视角，可用性问题会被熟悉度掩盖

### 缓解措施

针对过拟合这条（它是本决策最实质的风险）：

- **把团队习惯当作假设而非事实**。凡是"我们是这么做的"进入产品设计时，
  在 PRD 中显式标注为待验证假设，M3 引入试点团队时逐条检验
- **M3 必须引入 2–3 个外部试点团队**，不能一路自用到 M4
- Workflow Engine（M1）从一开始就做成可配置，不把我们的状态机写死成唯一状态机
- 定期请团队外的人做可用性观察，对抗熟悉度带来的盲区

### 需要后续处理

- [ ] M1 增加"可用 UI"作为交付项与出口标准
- [ ] 调整 M2 优先级：GitHub Connector 前置，Jira Connector 改为条件触发
- [ ] 在 PRD 中标注源自自身工作流的假设，建立待验证清单
- [ ] M3 前物色外部试点团队

## 验证方式

- M1 出口标准改为：**ProjectOS 自身的一个真实迭代**在系统内从 Requirement 跑到 Release
- 每迭代记录一次"绕开系统"的次数与原因，趋势应当下降；上升说明产品在退化
- M3 的 Automation Rate 数据来自真实交付，而非构造场景
