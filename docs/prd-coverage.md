## 这份表本身有多可信

统计口径：只算 Must（M）。Should / Could 另计。**Must 的总数（102）
与每模块的条数已经用脚本对着 PRD 核过，是准的**；
`pnpm lint:coverage` 保证合计等于各行之和。

但"已交付"这一列是人写的，而它已经被发现错过三次，
错法完全一样——**把一条 Should 当成缺失的 Must 写进了备注**：

| 行 | 原来写的缺口 | 实际 |
| --- | --- | --- |
| WF | SLA 超时、可视化编辑器 | 这两条是 S 与 C。真正缺的是 FR-WF-006 外部事件触发 |
| RES | FR-RES-010 事件订阅 / Webhook 出站 | 是 S。12 条 Must 全部交付 |
| ARCH | 按 BC 重组目录 | ARCH 的 Must 里没有这一条。缺的是 FR-ARCH-011 可取消 |
| IAM | OIDC、JIT 授权 UI、委派链 | OIDC 不是编号需求；FR-IAM-006 临时授权与 FR-IAM-007 委派交集都已交付 |

这四行的备注是**照着印象写的**，不是照着需求编号核的。
核对时确认缺失的两条现在都补上了：FR-IAM-012 blastRadius
（单次 Run 的影响面上限，动手之前判）、FR-ARCH-011 可取消。

**十行现在全部逐条核对过编号**，各有细分表。最后核对的是 ONT，
而它印证了前面那句话：**没核对过的行，数字只是个说法。**

ONT 记的是 7/7，而 FR-ONT-007（本体版本化与兼容策略，验收标准
「升级 minor 版本后旧数据可正常读取」）**当时做不到**——
`version` 只被校验了格式（像不像 semver），之后没有任何代码读它，
而注册表压根不允许升级：`registerEntity` 对已存在的类型直接抛错。

`EntityTypeDef.version` 上的注释写着「实例写入时记录 ontologyVersion，
读取旧实例时按兼容视图投影」，那两件事一件都没发生。
**和 `sla` 是同一个毛病**：一个看起来配置好了、实际什么也不做的字段，
比没有这个字段更糟，因为有人会以为它管用。

现在它是真的（见下）。数字仍是 7/7，但此前那个 7 是虚的。

"前两者的缺口是外部依赖，不是记错"这句话本身就是记错的，现在删掉了：
AI 那一行的九条里有六条根本不需要模型，CON 那一行的 GitHub 也不需要
真的连上 GitHub 才能验大部分。**"被外部依赖挡住"是这份表最舒服的一句话，
所以它最该被怀疑。**

**FR-ARCH-011 只按验收标准算交付，要说清楚边界。**
验收标准原文是「取消进行中的 Run，含 Connector 调用在 5 秒内全部停止」，
这一条有用例锁住：进程关停会打断在途的 Run，把 Run 迁到 Cancelled
也能被另一个进程里的运行时读到，取消之后不再写回、不再重试外部调用。

但需求正文写的是「**任何**超过 1 秒的操作接受 AbortSignal」，
而读路径（列表、图遍历、Automation Rate 的那次 N+1）目前**都不接受信号**，
客户端断开也不会停止查询。这一块没做，别把它当成做了。

核对 DOM 时抓到了这份表最坏的一种错：**代码引用了需求编号，做的却是别的事**。
`STORY_LIFECYCLE` 里写着 "FR-DOM-004"，守的是"有没有拆出任务"，
而 FR-DOM-004 说的是"必须含结构化 Acceptance"——Story 上根本没有这个字段，
本体里也没有 Acceptance 这个类型。一句写错了编号的注释比没有注释更糟：
它让人以为这条需求已经落地，于是不会有人再去看。现在它真的实现了。

写在这里而不是悄悄改掉数字，是因为这份文档唯一的用处就是可信。
一个被改对了但没人知道曾经错过的进度表，下次还会错。

### 最坏的一次：本地全绿，CI 连续四个 commit 是红的

前面几条都是"记错了"。这一条更糟：**报告出来的绿色是假的，而且假了四次。**

把 `playwright` 从 devDependencies 挪到 dependencies 时没有重新生成
`pnpm-lock.yaml`。CI 的第一步 `pnpm install --frozen-lockfile` 因此直接失败，
**一个测试都没跑到**，连续四个 commit。而本地 `pnpm check` 每次都全绿——
因为本地 `node_modules` 已经在了，install 根本不执行。

这不是运气不好。**本地的检查清单漏掉了 CI 的第一步，那本地的绿色就不代表任何事**，
而它读起来和真的一样。发现它靠的是去翻 CI 记录，不是靠任何一条检查报警——
换句话说，这个缺陷本身也是"缺信号"，和它造成的后果是同一个毛病。

修法有两部分：重新生成 lockfile，以及把 `lint:lockfile` 加进 `pnpm check`
并排在最前面。加进去之后种了一个缺陷验证过：往 package.json 里塞一个
lockfile 里没有的依赖，`pnpm check` 立刻红。

FR-ONT-007 的关键不在读路径。**旧数据能不能读，不取决于读的时候做了什么，
取决于升级的时候允许了什么**——读路径本来就不校验，旧行永远读得出来。
真正会出事的是下一次**写**：一次偷偷加了必填属性的 minor 升级，
会让每一条旧数据在下次更新时被拒，而报出来的错是"缺少必填属性"，
没有人会想到那是三个月前一次"兼容的"升级造成的。

所以 `compatibilityOf` 管的是**升级时拦住什么**：

| minor 可以 | minor 不可以 |
| --- | --- |
| 新增**可选**属性 | 新增必填属性 |
| 放宽枚举 | 收窄枚举（存量里的值会变非法） |
| | 删除属性（那个值就读不出来了） |
| | 改属性类型 |
| | 把可选改成必填 |
| | 缩小 maxLength |

`patch` 不允许任何模式变化——放宽的话 patch 和 minor 就没区别了，
而 patch 是唯一一种大家默认可以闭眼升的。
`major` 不做检查，**那正是 major 的含义**：破坏性变更不是不允许，
是要求它显式地表现在版本号上，于是"这次升级会不会弄坏旧数据"
从代码评审里的一个问题变成版本号上的一个事实。

升级是 `upgradeEntity`，和 `registerEntity` 分开：让 register 悄悄覆盖的话，
一次拼错的类型名会安静地替换掉另一个类型的模式，
而那要到第一次写入失败时才会被发现。

变异 14/14。第一轮 13/14——活下来的那条值得记：minor 回退
（`1.1.0 → 1.0.0`）的判断整个删掉，用例照样全绿，
因为它会被后面那条 patch 判断顺手拦下。补了 `1.1.0 → 1.0.5`
（minor 退、patch 进）之后才真正测到那一行。

`sla` 曾经是这份表里最典型的一处虚报：它在状态定义里、在类型里、
在 Task 的 `Doing` 上都写着，**但没有任何代码读它**——
一个看起来配置好了、实际什么也不做的字段，比没有这个字段更糟，
因为有人会以为超时会有人管。现在它由 `SlaSweeper` 巡检，
超时会生成通知或升级到值班，每一条都种过缺陷验证会红。

计时用单独的 `status_since` 列而不是 `updated_at`：后者被任何一次编辑刷新，
于是一个停滞三周、昨天被人补了个描述的任务看起来"刚动过"——
而那正好是最该报警的对象。

FR-WF-006 一开始也被记成"需要真实的 GitHub"，那是错的：
**GitHub 是发送方**。它拨这个号没法在这里验证，但接的这一半可以，
而且必须——验签、认出说的是哪个对象、翻译、进 outbox、跑自动化，
整条链没有一步依赖 GitHub 真的存在。用例发的是 GitHub 真实的
`pull_request` webhook 形状，断言的是"PR 合并后 Task 变成 Done"，
也就是验收标准的原文。

翻译层把外部载荷当**不可信输入**：先验签再解析、只带声明过的字段、
原始报文不落库（里面可能有 token 和整棵 diff）。
验签用 `timingSafeEqual`——字符串比较会在第一个不同的字节上返回，
于是签名可以按响应时间一个字节一个字节地试出来。

接 CI 或 Kafka 时加一条来源配置即可，翻译层不需要改。

RES 这一行此前记的是 **11/12，缺「FR-RES-010 事件订阅 / Webhook 出站」**。
和 WF 那行是同一个毛病：FR-RES-010 是 **Should**，不是 Must。

顺带把 FR-RES-011 从"人工审查"变成了机器做的事。它的验收标准原文是
「端点清单审查通过」，而人工审查有个众所周知的性质：第一次做得很认真，
然后就不做了。`tests/integration/endpoint-inventory.test.ts` 把实际路由树

"人也走这条路吗"。种过一条 `POST /v1/agents/:id/run` 验证它会触发。

| FR-AI-007 无出处的内容标注「待确认」 | ✅ 标注而非删除，成文后复查，出处落成 derivedFrom 边 |
| FR-AI-009 推荐带出处与时效，点击率可统计 | ✅ 检索排序是确定性的；推荐是领域对象，点击率即查询 |
| FR-AI-010 行动项一键创建并关联负责人 | ✅ 没有负责人的不建，但**还给使用者**而不是丢掉 |
| FR-AI-003 自动估点并给出类比依据，中位偏差 ≤ 1 档 | ✅ 类比检索，不是生成；留出法实测 0 档，成色见下 |

FR-AI-001 是这一行里第二次纠正判断。它的验收标准是
「生成对象树并**可逐节点接受/拒绝**」——那是**机制**，不是模型输出质量。
和整个 Agent 运行时一样，用确定性模型就能完整验证（运行时 11/11 就是这么测的）。
把"需要模型才能产出好内容"和"没有模型就做不了也验不了"混为一谈，
是我先前把这一整块记成 ❌ 的原因。

改动本身：Draft 模式不再直接创建目标对象，而是一个节点落一条 `Proposal`。
接受时才真的创建，走的是普通 `create`，所以本体校验、权限、审计、事件一个不少——
**Agent 提议的对象和人建的对象没有区别**，只是多了一步谁来点头。
原先那条"Draft 直接落库"的用例因此红了，那正是这次改动的意义：
只能对整棵树表态的话，实际结果是全都不要。

这一段上一版写的是「其余几条按理也能验证，本轮没排上」，然后我把
002 / 004 / 007 / 009 / 010 一律记成了 ✅。**那是虚报，现在改回来了。**

写出来的是它们的**验收口径**——覆盖率、依赖与 capacity、出处标注、
时效、负责人——一组纯函数，有用例、过了变异测试（19/19）。
但这些需求要的是**能力**（拆需求、排 sprint、写 PRD、推荐知识、抽行动项），
而能力要模型。**把"验收标准可判定"当成"需求已交付"，是这份表犯过的
同一类错的新变种**：前几次是把 Should 当 Must，这次是把尺子当成了被量的东西。

所以它们记 ⚠️，按本表规矩不计入。口径留着，等生成侧接上时它就是现成的闸。

**FR-AI-009 是第六次。** 「知识主动推荐」的验收标准是
「推荐带出处与时效，**点击率可统计**」——说的是**检索与留痕**，不是生成。
"主动推荐"要的是把库里已有的知识在对的时候摆到人眼前，不是现编一段内容。

排序用三个信号，各防一种失败：词面重合防"推了一堆无关的"，
图上相邻防"只会按关键词匹配、看不见同一个项目里刚踩过的坑"，
新鲜度防"推了一条三年前的、当时是对的"。出处与时效这道闸在**排序之前**：
排完再筛会让"扣下了几条"混进"排在后面"里。

分数低于下限就不推。**宁可少推，也不要用噪音换展示量**——
一个推错过几次的推荐位之后就没人看了，而它仍然会在指标上显示"有展示量"。

「点击率可统计」这半句决定了推荐要做成**领域对象**而不是埋点日志：
推荐被点了没有，就是它现在处于哪个状态，于是点击率是一次普通的分组计数，
和别的指标走同一条路径——**系统里不需要为它新开一条写路径**
（FR-DASH-005 的原话是"指标由事件流自动物化，无人工填报"）。
分母是**已表态的**（Clicked + Dismissed）而不是推过的总数：
用总数的话，刚推完一批点击率就掉，而那只说明推得及时。

这一轮差点又加了一个 `sla` 式的死字段：`Recommendation.shownAt` 配着
`Shown` 状态的 entry action。它**永远填不上**——entry action 只在迁移进入
某状态时运行，而初始状态是创建时直接落的，不走迁移。
用例把它逼出来了，字段删了，展示时刻用资源自带的 `createdAt`。

变异 11/11。第一轮 7/11，四条活下来的里有一条是**真 bug**：
注释写着"除以被推那条的词数是为了不让长文档吃亏"，而代码做的正是
让长文档吃亏的那件事。现在分母是**当前对象**的词数——
问的是"这条知识覆盖了我正在看的东西的多少"。

**FR-AI-004 是这一行第五次纠正判断，而且是最不该错的一次。**
它的验收标准是「生成 ≥2 个候选方案，不违反依赖与 capacity 约束，
可一键应用与撤销」——那是一个**排程问题**，不是一个语言问题。
把它记成"要真实模型"，等于没读需求就归了类。

用模型做排程换来的是一个偶尔排出违反依赖的方案、而且说不清为什么
这么排的排程器。模型在这条需求附近能帮上忙的地方是**估点**
（FR-AI-003），不是排程本身。

三个策略各回答一个不同的问题——**候选之间必须真的不同**，
三份大同小异的方案不是"给了选择"，是把同一个决定说了三遍：

| 策略 | 它回答的问题 |
| --- | --- |
| value-first | 这个 sprint 我最想拿到什么？ |
| unblock-first | 做什么能让后面的人最快开工？ |
| quick-wins | 怎么让这个 sprint 结束时"完成"的条数最多？ |

**"一键撤销"是这条需求里真正有分量的部分。** 没有它，一份候选方案就不是
"可以试试的方案"，而是一次要开会决定的变更——而要开会决定的东西，
没人会为了比较两个候选而各试一遍。**撤销的成本决定了尝试的意愿。**
撤销靠一张明确的清单，不是靠时间戳：按时间回滚会连带撤掉别人在这中间
做的改动，而那种错误发生时没有任何提示。

写排程器的过程逮到了**校验器自己的一个真 bug**：
`validateSprintPlan` 把"依赖不在这个 sprint 里"一律判为违规，
而依赖已经在上个迭代交付掉是最常见的情况——那个版本会把
**几乎每一份真实方案**判成非法。生成侧和判定侧一起写，
才会有人真的去问"这条规则在真实数据上成立吗"。

FR-AI-006 是这一批里唯一真正交付的，而它的第一版实现也是错的，
值得完整记一笔：

- 第一版是 Agent 运行时里的一个产出闸，检查 `attributes.evidence` 空不空。
- Risk 的本体里**根本没有这个属性**，于是那个闸会拒掉每一条风险提议——
  一个把功能彻底关掉的"校验"。
- 就算加上，一个字符串数组也**点不动**。「可点击到实体」在这个系统里
  的意思是**关系**。
- 现在它是 Risk 生命周期上的 `hasRelation: evidencedBy` 守卫，
  和 Knowledge 的来源守卫（FR-DOM-008）同一套机制。好处不只是对：
  它对**所有**风险生效，Agent 建的和人建的一视同仁。

闸设在 `Mitigating` 而不是 `Identified`：刚发现时说不清出处是正常的，
设在入口会让人不敢登记风险，而**漏登记比登记得潦草糟得多**。
但要动手缓解、要占用人和时间，就得说清楚是什么让你这么判断的。

单开 `evidencedBy` 而不复用 `derivedFrom`，是因为复用要把后者的值域一起
放宽，那会**顺手改掉 Knowledge 的不变量**——一次为了少写十行做的语义变更，
事后没人记得是这么来的。

`requireEvidence` 那个校验函数因此删了。**建了之后发现正确实现在别处，
该走的是它，不是让它留在那儿**——留着就成了下一个"看起来有人管"的东西。

**002 / 007 / 010 是最后三条，和 FR-AI-001 完全同类。**
它们的验收标准写的都是机制：覆盖率与未覆盖项、无出处内容的标注、
行动项一键创建并关联负责人。**没有一句在说模型答得好不好。**

三条路径的共同点是**闸设在落库之前**，而且不合格的部分要逐条说出来：

- **拆 Story 先验覆盖率再建**。先建后验的话，不达标时库里已经躺着
  一批半成品，清理它们要么靠人、要么靠一段回滚代码——
  而回滚代码的失败恰恰发生在最不该失败的时候。不达标就**一条都不建**。
- **无出处的陈述标注而不是删除**，而且**成文之后再复查一遍**。
  只在生成时打标记的话，将来改渲染的人会在毫不知情的情况下
  把这条需求废掉。有出处的那些同时落成 `derivedFrom` 边——
  Knowledge 想进 Published 本来就要求它（FR-DOM-008），
  在这里建好是让这份文档从一开始就满足系统自己的不变量。
- **没有负责人的行动项不建，但要还回去**。那句话在会上是有人说过的，
  使用者可能只是想补一个负责人；悄悄扔掉的话，他会以为系统没听见。

变异 9/9。还剩一条**没有用例能触发**的断言（成文后的复查），
在代码里写明了：它现在确实测不到，留着是因为渲染和校验会各自演化，
而它们对不上的表现是"文档里有几句没有标记"——一种没人会注意到的失败。

**FR-AI-003 是第七次纠正判断。** 它确实需要**数据**，但不需要**生成**：
「给出类比依据」这句话本身就说明了做法——找出以前做过的相似的事，
看它们当时是几点。检索加统计。

不用模型的理由不是省事：估点的可信度来自"凭什么这么估"。
模型给一个数字加一段说辞，人无从核对；给出三条以前的相似任务
和它们当时的点数，人能一眼判断这个类比成不成立——
**而能被判断的估算才有资格影响排期。**

验收标准「中位偏差 ≤ 1 档（3 迭代样本）」的验证方式，
参照的是同一张需求表里 FR-AI-008 的「识别率 100%（**测试集**）」——
PRD 自己认可用测试集验准确度类指标。留出法：前两个迭代当语料，
第三个迭代当留出集，实测**中位偏差 0 档**，8 条给出估算、1 条弃权。

**成色说清楚**（`tests/fixtures/estimation-corpus.ts`）：
语料是种出来的，不是生产数据，而且**比真实 backlog 容易**——
三个迭代做的是同一类活，措辞高度平行，"找相似的"本来就好做。
那个 0 说明的是这个方法在同质 backlog 上成立，
不说明一个什么都做的团队也有这个成绩。真实数据接进来之后这个数字
大概率会变差，**而那时该改的是方法，不是换一份更容易的语料**。

几个决定：

- **用中位数不是平均数。** 历史数据里一定有标错的（语料里就故意埋了一条
  被标成 13 点的小活）。平均数会被它拽走一大截。
- **找不到可比的就弃权，不猜。** 给一个默认值会让人以为系统看过历史了，
  而它什么也没看到。弃权数单独报出来——这个数字大本身就是个问题。
- **弃权不计入中位偏差。** 计入的话会逼着系统去猜；不报出来的话，
  一个"只在特别有把握时才估"的系统能拿到漂亮的中位数而什么忙也没帮上。
  所以两个数字都给。
- **档位对半时往上取。** 估少了是承诺了做不完的量，而那要到迭代末尾
  才暴露出来；估多了只是这个迭代少排一件事。

变异 12/12。第一轮 8/12，活下来的里最危险的一条：留出集为空时
`median([])` 返回 0，于是**一次什么都没估的评估会显示"中位偏差 0 档"**——
完美通过验收标准，而它一条都没算过。现在返回 Infinity。

FR-AI-013 要说清楚主防线在哪：**结构性的那一层**——模型的动作空间是一个
封闭联合（finish / propose / call），能提议什么由 Agent 声明的 `mayPropose`
限死，能调什么工具由连接器白名单限死。注入成功也拿不到新权限。
文本中和是第二层，防的是"检索来的内容冒充系统在说话"：
即使拿不到权限，一段写着 `### system:` 的需求描述也足以让模型误解自己的角色。

「指标即查询」的代价要说清楚：现算在百万行规模上没问题
（[性能基线](perf-baseline.md)里列表查询 P95 约 20ms），
再大一个量级就需要物化。届时这份指标定义就是物化任务的输入，
不需要重写口径。

Agent 视角凑齐 8 项时给指标模型加了**求和 / 求平均 / 比率**——
数条数答不了"花了多少钱"。加的是动作种类，不是自由度：
仍然只接受属性名，不接受 `sum(cost * 1.2 + fee)` 这类表达式。
一旦允许表达式，指标就不再是"能被读懂、被复算、被质疑"的东西了。

补齐 Project 与 Team 视角时，差的不是代码而是**对象**：
Velocity 要有 Sprint，Milestone / Risk / Budget 各自要有类型。
先建类型再补指标是对的顺序——反过来做只会得到几个恒为零的数字，
而恒为零的指标比没有指标更容易让人误判。这四个类型按 PRD 03 的
关键属性与不变量建出来了，其中 Risk「高风险必须有 owner 与 mitigation」
做成了 `Mitigating` 状态的守卫：登记一条风险不该有门槛，
但声称"正在缓解"就必须说得出对策。

Cycle Time 与 Lead Time 目前只给出**计数**，没给时长分布。
`status_since` 已经在库里（007_sla.sql），把它展开成分布是下一步——
现在的口径写在指标定义里，没有假装它是分布。

**Automation Rate 是唯一的例外，它明显更贵**：每个工作项都要拉一次历史
再算一次编辑距离，是一次 N+1。目前用一条 5,000 项的硬上界兜住，
命中时响应里的 `truncated` 为 true——**少算可以，不声不响地少算不行**。
这一条是已知的、要还的债，不是"没想到"。

这张细分表是逐条列出来才发现的：CON 原本记的是 8，而按编号数是 7
（加上 Browser 那两条才是 9）。和 AI 那一行一样，多出来的那个 1
从来对不上任何编号。`lint:coverage` 现在会比对"某一行 vs 它自己的细分表"，
所以这类漂移当场就红。

把这些一律写成"被外部依赖挡住"是不诚实的——**手边有的东西不算阻塞**。
Browser 就是例子：Chromium 一直在这台机器上，写完之后端到端跑通了，

MCP 也做完了：不引第三方 SDK，自己实现 initialize / tools/list / tools/call

14 条用例红了 8 条。

「接入**任意** MCP Server」这句话的代价要写清楚：server 是别人写的代码，

工具不默认可用（白名单之外一个都调不了）、
**不默认只读**（没有显式 `readOnlyHint` 的一律当 action，因而走人工确认）、
返回内容一律按 confidential 脱敏。反过来设的话，
接一个新 server 就等于把它声明的一切直接授权给 Agent。

Browser 连接器落地时顺带抓出三个真问题：

`https://api.example.com:8443/…`；参数校验排在开浏览器之后，
一次少写 selector 的调用要先花几百毫秒拉起 Chromium 才报错；
以及 `src/` 依赖了一个 devDependency——分层检查当场拦下，
那正是它存在的理由。

契约已经把它们变成薄薄一层：实现 `Connector` 接口，声明操作与白名单即可，
授权、审计、幂等、限流、退避、熔断、脱敏全部由网关提供。

### FR-CON-007：演练跑通了，成色写清楚

验收标准是「**完成** 3 阶段迁移演练，无数据丢失」。它要的是一个
**已经发生的事件**——所以关键问题是：什么样的一次运行才算"演练"。

上一版记 ⚠️，理由是"对着内存里的假源跑一遍不是演练"。**那个理由是对的**，
而它指出的正是当时缺的东西：假源把**分页、认证、字段裁剪、错误映射、
反向映射**整段跳过了，而迁移工具丢数据恰恰最常丢在分页上。

现在演练跑在 `JiraSource` 上：真的发 HTTP、真的翻页（五条记录、
一页两条、翻三页）、真的 PUT 回写，对面是一个在监听的、讲 Jira 协议的
服务器。三个阶段一次跑完，对账 `missing` 为空。
**这条路径就是生产里会跑的那条**，区别只在端点指向哪里。

把演练搬到真 HTTP 上，当场逼出一个真 bug——而它是这一条最好的
存在理由：一个**忽略 `startAt`、每次都返回第一页**的服务器，
会让"读到的条数对不对得上 total"那个检查**顺利通过**，
因为它累加到 total 条就停了，而那 total 条是同一条复制了 total 遍。
**迁移里"数据翻倍"和"数据丢失"一样糟，而且更难发现：对账会说一条不少。**
现在同一个 key 回来第二次就抛。内存假源永远测不出这个。

⚠️ **还剩什么没验**：对面那个服务器讲的是 Jira 的协议，
但报文形状来自公开文档，不是从一个真实实例上抓的——
GitHub 那组用的是从本仓库 CI **真抓**下来的报文，两者不是一个成色。
整条管线验到位了，**"Jira 真的长这样吗"没有**。
接一个真实例时，第一件该做的事是抓一份真报文回来替掉 fixture。

已经做完并验过的部分（`src/domain/migration/sync.ts`、
`src/infrastructure/connectors/jira.ts`）：

| 这一段 | 状态 |
| --- | --- |
| 三阶段各自允许的写方向（mirror 只读 / parallel 双向 / cutover 不回写） | ✅ 16/16 变异 |
| 冲突**必须被发现**，不按时间戳悄悄合并 | ✅ 说得出哪几个字段对不上 |
| 阶段传不动的改动记成 `held` 而不是 `noop` | ✅ 这条是全组最重要的断言 |
| 对账证明没丢东西（missing / diverged / extra 分开） | ✅ 条数对得上 ≠ 没丢 |

几个决定：

- **没有"自动解决冲突"这一档。** 两边都改了同一条记录就是有人要做决定。
  按时间戳挑赢家看起来省事，代价是另一边那次修改**无声消失**——
  而那正是"无数据丢失"要防的东西。
- **同步引擎不认识 Jira。** "东西有没有丢"是引擎的性质，和源系统是谁无关。
- **未映射的字段和状态一律报错。** 迁移工具最危险的性质是"尽力而为"：
  它会成功，而且看起来对。自定义字段是丢数据的重灾区，
  而丢了不会有任何痕迹。
- **分页读到的条数必须和 Jira 报的 total 对上。** 少读一页不会报错，
  后面的对账会把它报成"源系统里少了这些"——那时人会去查 Jira，
  查的是一个根本没出问题的地方。
- 「不迁移这个字段」要写进 `ignore` 名单。**让它成为一个有人写下来的决定，
  而不是一次遗漏的默认结果。**

演练现在**跑得起来**，而且跑在真库上（`tests/integration/migration-rehearsal.test.ts`）：
走普通的 `service.create` / `update`，本体校验、生命周期守卫、权限、审计
一个不少。另开一条迁移专用写路径能省事，代价是迁进来的数据
**从第一天起就不满足系统自己的不变量**，之后所有守卫在这批数据上都失效——
它们只挡后来的人。所以：**迁移不过去的数据是这次迁移的问题，不是守卫的问题**，
报告里 `rejected` 那一栏就是给这个用的。

把它接起来的过程被系统自己纠正了四次，每次都是它对：

1. **RLS 拦下了审计落盘**——独立事务忘了带租户上下文。
   这正是 FR-IAM-015 想要的表现：漏配租户不是"写进了别人的库"，是写不进去。
2. **deny-by-default 拦下了创建**——光有 capability 不够，还要有策略。
   于是迁移作业成了一个**显式的系统身份** `system://migration`，
   权限和自动化那个不同：自动化能推状态不能创建，迁移能创建能改
   **不能推状态**。让迁移推状态机等于给它一把绕开所有守卫的钥匙，
   而迁移正是最想绕开守卫的那个场景（"这批老数据不满足新规则"）。
3. **本体拦下了 `status` 当属性写**——源那边状态是个字段，这边它是资源状态。
   区分出一条真正的规则：**建在某个状态上 ≠ 迁移到某个状态**。
   Jira 里已经在做的任务搬过来就该是 Doing，让它落在 Todo 再由人一条条推，
   那不是迁移是重录一遍；但建完之后就不能再推了。
4. **对账一开始双向比字段**，于是本地必然多出来的 status / owner
   让每条记录都显示为分叉。改成**只比源声明的字段**：
   源是迁移期间的模式权威，而一份永远脏的对账等于没有对账。

`Principal` 因此从三种变成四种。它是个封闭联合而不是 `string`，
所以加一个后台作业必须改类型——**那正是要的效果**：
新作业的权限边界得有人看一眼，而不是起个名字就能行动。

| 三阶段演练走真 HTTP（翻页 / 认证 / 回写 / 反向映射） | ✅ 一次跑完三个阶段，对账 missing 为空 |
| 分页卡住时不静默重复 | ✅ 同一个 key 回来第二次就抛 |

### FR-CON-006 的成色，说清楚

验收标准是「可创建 PR、读取 CI 状态并回写 Task」，三段分别是这么验的：

| 这一段 | 怎么验的 | 需要 GitHub 在场吗 |
| --- | --- | --- |
| 创建 PR | 本地 HTTP 服务器逐字断言方法、路径、版本头、报文 | 否 |
| 读 CI 状态 | 报文是**从本仓库自己的 CI 真实抓下来的** | 否 |
| 回写 Task | 真数据库、真生命周期守卫、真审计 | 否 |

**没有覆盖的是：github.com 会不会接受这些请求。** 拿不到产品自己的凭据
（会话里那个 token 属于这次会话，不属于 ProjectOS——用它写出来的用例
只在这个沙箱里绿），这一条就验不了。所以这个连接器和 MCP（对面是真 server）、
Browser（对面是真 Chromium）**不是同一个成色**，别当成一样的。

fixture 用真抓的而不是手写的，是因为手写 fixture 等于把"我以为它长这样"
当成事实来测。真抓的那份里有一条 `in_progress`——手写的话大概率只会写
success 和 failure 两种，而"还在跑"恰恰是判断逻辑里最容易错的一档。

三个值得记的决定：

- **白名单的单位是 repo，不是 host。** 按 host 的话，"允许访问
  api.github.com" 等于把账号下每个仓库都授权出去了——那不是任何人
  想批准的那件事。
- **GitHub 的九种 conclusion 收敛成三种**（passing / failing / pending），
  且用白名单：未知的结论一律算失败。GitHub 将来加一种时，**误报比漏报安全**。
- **CI 绿了不自动推进任务**。CI 通过只说明代码能编译能跑测试，不说明这个
  任务做完了。自动推进会让"完成"这个信号变得不可信，而那是看板上最重要的信号。
  唯一的例外是解除**它自己打的**那个阻塞——而"自己打的"要真的查一下
  blockReason 的前缀：一个因为"等第三方接口"被人挂起的任务，
  不该因为 CI 变绿就被放回去。

变异测试 20/20。第一轮 18/20，两条活下来的都是用例太弱：
一条把阻塞原因断言成"含 CI 两个字"，于是把原因换成光秃秃的「CI 失败：」
照样通过——而那对着手修的人一点用没有；另一条只测了"出发前就已取消"，
没测**已经在等**的那次，而验收标准要的正是后者。

### FR-ONT-011 / FR-RES-009：候选集是这条路径上唯一要判断的事

打分函数早就有了，接进产品时真正要想的是**库里的对象怎么变成语料**：
全租户喂给检索没有上界，而拿整句话去检索几乎什么都匹配不到
（「这个项目的灰度策略是什么」作为子串不会出现在任何对象里）。
所以先把问句切词，每个词各查一次再取并集——词面召回交给数据库。

第一版取问句**最前面**六个词，那是错的，而且错得很安静：
「我们这套系统的数据库连接池默认开多少个连接」的前六个二元组是
我们/们这/这套/套系/系统/统的，全是引子，「数据库」「连接池」一个都轮不到。
表现是**永远答不出来**，而它看起来和"库里确实没有"一模一样。

代价要说清楚：这是最多 24 次查询，而中文二元组短于三字符、走不了
trigram 索引，不带 `type` 收窄的话每一次都是一遍全租户扫描。
端点上因此留了 `type`——知道自己在找什么的调用方应该说出来。

验收标准里那个 ≥ 90% 现在是**对着库里的真实对象**量的（十篇文档、
十个问题），而不是只对着一份 fixture 语料。后者证明的是打分函数，
不是这套东西在库里的表现。

### FR-ONT-008 / FR-ONT-009：都是"每次现读"

两条都没有缓存，而这是有意的。状态机那边用 TTL 缓存是因为每个请求都要全量取；
规则和扩展一个租户各只有几行，为它们省一次小查询而引入一层可能不一致的缓存，
换来的是**"我改了但没生效"**——一个查起来极难的问题。
「变更即时生效」的全部内容就是这个"现读"。

FR-ONT-008 有三个决定：

- **规则建的边是建议，不是事实。** 新增了 `rule:<ruleId>` 这个来源，
  和 `agent:<name>` 归成一类：默认待确认、必须带置信度。
  图上的边会被守卫读（Release 只装 Done 的 Task、Story 要有验收标准）——
  直接当成已确认的话，一条随手写的规则就能让一批对象的状态机行为整个变掉。
- **一条边建不成，不能把别人的写入带走。** 用户只是改了个标题，
  不该因为某条规则指向一个不存在的 id 而失败。
- **但安静地跳过等于这条规则根本不存在。** 每一次跳过发一个
  `RelationRuleSkipped` 事件，于是"这条规则一直没建成过任何边"
  变成一个查得出来的事实。而咽下的那一档**只有两种**（目标不存在、
  领域规则不允许），其它一切往上抛——把它们也咽掉的话，
  一次真正的故障会表现为"规则今天没建边"。

FR-ONT-009 最容易错的一处是**拿什么当基底去校验**：用已扩展的注册表判，
第二次 PUT 会把自己上一次加的字段当成"已存在的属性"而拒绝。
变异测试专门种了这一条。

### FR-WF-010 / FR-WF-011：`advance` 和执行器为什么是两层

    advance    决定做什么（纯函数、可重入、逐条可测）
    executor   把它做掉、把结果记下来（有副作用、要处理失败）

合成一个的话，"这个流程的下一步该是什么"就只能通过跑一遍副作用来验证。

四个决定：

- **每做一步就落库。** 一个流程实例会跨天（人工节点等 24 小时、
  灰度观察好几轮），进程重启、部署、崩溃都会发生在中间。
  状态只活在内存里的话，一次重启会让一个已经冻结了 Release、
  已经调过部署接口的流程**从记录上彻底消失**——而外面的世界已经变了。
- **动作走的是同一个 `ResourceService`**——同一套守卫、权限、审计。
  另开一条"流程引擎直接改状态"的近路会省几十行，代价是流程绕过了
  状态机守卫，而守卫正是"Release 只能装 Done 的 Task"这类规则的所在地。
  一个能绕过它们的执行器，会让那些规则变成建议。
- **`compensation-failed` 是独立的一种结局**，不和 `compensated` 混在一起。
  它是唯一一种需要人立刻去看的状态：一部分副作用撤销了、一部分没有，
  系统在一个没人描述过的地方。
- **超时要有人兑现。** 定义里写了 `timeoutMs`，但没有巡检去驱动的话，
  一个等人的实例会永远挂着，攥着一个已冻结的 Release——没有任何报错。
  巡检自己不判超时，把实例交给 `drive`，由 `advance` 按 `onTimeout` 决定。

变异 7/7，但前三条是补了一组**不连数据库**的用例之后才逮到的。
它们证明的是三件"跑起来之后看不见"的事：每步落库（只有崩在中间时
才看得出来，而崩溃没法在集成测试里制造）、拒绝要变成失败的步骤结果、
循环体里的步骤 id 带 `#loop#round` 标签而补偿表按裸 id 建——
不剥标签的话，**灰度里做过的每一件事都撤不回来**，
而灰度恰恰是这个流程里唯一会真的改动线上流量的部分。

### 变异测试自己的一个洞

`tools/mutate.ts` 此前**不跑基线**。写 FR-ONT-011 的用例时有一条断言
在没种缺陷的时候就是红的（排序的兜底比较的是 id 前缀，`kn_` 永远排在
`task_` 前面，和创建顺序无关），于是每一个变异都"被逮到了"，
报告是漂亮的 7/7——而它一个缺陷都没检验。

**一个总是红的用例和一个总是绿的用例，在这个工具眼里没有区别**，
而后者至少还会被人注意到。现在每份 spec 先跑一遍原代码，
基线不绿就直接判这份 spec 的结论无效。

顺带删掉了一条变异（"文本里带上属性名"）：候选召回走的是仓储的
`search_text`，它本来就不含键名，所以**打分环节混不混进键名根本没机会显形**。
为它造一个能显形的用例只造得出一个脆的。删掉比留一条测不到的断言诚实。

### 这一轮里被逮到的

FR-ONT-012 落地时撞出三个缺陷，都不在新写的代码里：

- **`follow` 的请求上限是 10，而本体声明了 28 种关系。** 前端只能
  `slice(0, 10)`，被切掉的 18 种里就有 `decomposedInto`——一张少了
  大半种关系的图不会报错，只会**看起来是全的**。现在省略 `follow`
  就表示「全部」，意图能直接说出来，而不是让每个调用方自己去枚举。
- **`.board` 的 `overflow-y: hidden`。** 那套横向列布局是给"列"设计的：
  列自己纵向滚，容器不滚。七个状态的状态机放进去，Done 落在视口外面，
  **既不换行也滚不到**，而页面看起来完全正常。
- **UI 用例文件之间抢同一个数据库。** `setupTestDb()` 每次
  `DROP DATABASE ... CREATE DATABASE`，用的是同一个库名，而 `node --test`
  默认按核数并行跑文件。这个竞态一直都在，加第三个文件时才撞出来。

变异测试 6/6（subgraph）+ 3/3（诱导子图的取边）。两条一开始活下来的：
节点的 `depth` 全算成 0 没有任何用例发现——而图正是按它分层画的，
全 0 意味着所有节点叠在圆心上；以及"空节点集提前返回"看着像是省一次往返，
其实是唯一没炸的那条路（Kysely 的 `in []` 生成 `in ()`，PG 直接语法错误）。
