# ADR-0008 · 模块化单体，按限界上下文分模块

| 项 | 值 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-08-03 |
| 决策者 | 架构组 |
| 关联需求 | FR-ARCH-001, FR-ARCH-009, NFR-OPS-004 |
| 解决问题 | Q-A4 |
| 依赖 | [ADR-0007](0007-typescript-server-stack.md) |

## 背景

PRD 03 划出了 7 个限界上下文。一个自然的推论是"7 个微服务"——但那是把**逻辑边界**
和**部署单元**当成了同一件事。

现阶段的实际情况：

- 团队规模小，没有多团队并行开发同一系统的协调压力
- 领域模型还在演进，跨上下文的边界会反复调整
- M0 的全部数据都在一个 PostgreSQL 实例里，跨上下文查询是普通 JOIN
- 微服务的代价（分布式事务、服务发现、跨服务调试、N 份 CI/CD）现在全是净损失

同时 [ADR-0007](0007-typescript-server-stack.md) 已经确定了一件事：
**Agent Run 不能在 API 进程内执行**。Node 是单线程事件循环，长时任务会阻塞所有请求。
所以"单体"从一开始就不是单进程。

## 决策

**一个代码库、一个可部署单元、按限界上下文分模块；运行时分两种进程角色。**

### 代码组织

```
src/contexts/<bounded-context>/     每个 BC 一个模块
  ├── domain/       聚合、不变量、领域事件
  ├── ports.ts      该 BC 对外声明的接口
  └── adapters/     实现
```

M0 当前是按技术分层（`domain/` `infrastructure/` `api/`），
在 M1 引入 7 个 BC 时按上表重组为「先按 BC，再按层」。

### 模块间通信规则

| 允许 | 禁止 |
| --- | --- |
| 通过 Domain Event（outbox）异步交互 | 直接 import 另一个 BC 的 domain 内部 |
| 通过对方显式导出的 `ports.ts` 只读查询 | 直接读写另一个 BC 的表 |
| 引用另一个 BC 对象的 ID + 快照 | 跨 BC 的数据库事务 |

**关键约束：跨 BC 一律按最终一致处理，不使用跨模块事务。**
这条现在是自律，将来拆分服务时它就是拆分成本为零的原因——
如果现在允许跨 BC 事务，拆分时每一处都得重写。

由 dependency-cruiser 在 CI 中强制（FR-ARCH-001）。

### 运行时进程角色

同一份代码，按启动参数扮演不同角色：

```
┌──────────────┐   队列   ┌──────────────────┐   ┌─────────────┐
│  api         │ ───────► │  agent-worker     │   │  poller     │
│  只做 I/O    │          │  执行 Agent Run   │   │  发布 outbox │
└──────────────┘          └──────────────────┘   └─────────────┘
        └──────────────────────┬────────────────────────┘
                          PostgreSQL
```

| 角色 | 何时引入 | 理由 |
| --- | --- | --- |
| `api` | M0 ✅ | HTTP 入口 |
| `poller` | M1 | 消费 outbox，触发自动化 |
| `agent-worker` | M3 | ADR-0007 的硬性要求：长时 Run 不得阻塞事件循环 |

这三者共享代码与数据库，独立伸缩、独立崩溃。
"模块化单体"指的是**代码与数据的组织方式**，不是"只能跑一个进程"。

### 何时拆分为独立服务

不按感觉拆。满足以下任一条件才启动拆分讨论，并需要新的 ADR：

| 触发条件 | 说明 |
| --- | --- |
| 伸缩曲线分叉 | 某个 BC 的资源需求与其余部分相差一个数量级 |
| 团队协调成本 | 同一模块上并行开发的人数持续 > 8，合并冲突成为常态 |
| 合规隔离 | 某个 BC 需要独立的数据驻留或审计边界 |
| 故障域 | 某个 BC 的故障反复拖垮全局，且无法在进程内隔离 |

"代码变大了"、"看起来该拆了"不是触发条件。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| A. 微服务优先（7 个 BC → 7 个服务） | 边界物理隔离，独立伸缩 | 分布式事务、跨服务调试、7 套 CI/CD 与运维；领域边界还在动，改一次边界要改多个仓库 | 现阶段代价全是净损失 |
| **B. 模块化单体 + 多进程角色** | 迭代快、调试简单、边界靠 CI 强制；拆分成本被前置压低 | 边界靠纪律维持，纪律松了会退化成大泥球；单点部署 | **已选**，靠 dependency-cruiser 把纪律变成机器强制 |
| C. 纯单进程单体 | 最简单 | 与 ADR-0007 冲突：长时 Agent Run 会阻塞 API | Node 运行时特性直接排除 |

## 后果

### 正面

- 跨 BC 重构是一次 IDE 操作，不是一次跨仓库迁移——领域模型还在演进时这点极其重要
- 一个数据库、一次事务、一次部署，M0/M1 的复杂度全部花在业务上
- 端到端调试不需要分布式追踪就能做
- 边界由 CI 强制而非文档约定，退化会在 PR 阶段暴露

### 负面 / 代价

- **边界靠纪律**：dependency-cruiser 能挡住 import，挡不住"在同一个事务里顺手改了两个 BC 的表"。需要在 code review 中盯住
- 单一部署单元：任何模块的变更都要整体发布，发布频率受最慢的模块牵制
- 单一数据库：某个 BC 的慢查询会影响全局，需要靠 statement_timeout 与连接池配额兜底
- 伸缩粒度粗：只能整体扩容 api 进程，不能只扩某个 BC

### 需要后续处理

- [ ] M1 重组目录为「先 BC、后层」，并补 dependency-cruiser 的 BC 间规则
- [ ] 增加一条 CI 检查：跨 BC 的数据库事务（同一事务里写多个 BC 的表）
- [ ] 进程角色的启动参数与部署清单（M1 引入 poller 时）
- [ ] 连接池按角色分配配额，避免 worker 抢占 api 的连接

## 验证方式

- CI：dependency-cruiser 阻止跨 BC 的内部 import（M1 起）
- CI：跨 BC 事务检查（待实现）
- 演练：从任一 BC 中挑一个，验证它能在不改动其他 BC 的前提下被抽出为独立服务——
  抽不出来说明边界已经退化，这是拆分成本的真实度量
