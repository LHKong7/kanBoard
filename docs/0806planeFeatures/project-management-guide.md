# 用 Plane 做好项目管理：实践指南

> 配套文档：[产品功能清单](./product-features.md)
> 本指南只使用本仓库（社区版）**已实现**的能力，付费版功能会单独标注。

---

## 一、先理解 Plane 的四层结构

用错层级是绝大多数团队用不好 Plane 的根因。Plane 的层级是**固定四层**：

```
Workspace（工作区）    →  一个公司 / 一个部门，全员共享成员池与计费
  └── Project（项目）   →  一条产品线 / 一个团队，独立的编号前缀与权限
        ├── Cycle（周期）   →  时间盒（Sprint / 双周迭代），横切
        ├── Module（模块）  →  交付物 / 里程碑，纵切
        └── Work Item（工作项）→ 最小执行单元
```

**关键认知：Cycle 与 Module 是两个正交的维度。**

| | Cycle（周期） | Module（模块） |
| --- | --- | --- |
| 本质 | **时间**维度 | **范围**维度 |
| 回答的问题 | "这两周做什么？" | "这个功能做完了吗？" |
| 是否有明确起止 | 有（start_date / end_date） | 有（start_date / target_date），但可长期 |
| 状态 | 由日期推导（未开始/进行中/已结束） | 显式六态状态机 |
| 一个工作项能属于几个 | **1 个**（互斥，加入新周期会自动从旧周期移出） | **多个**（`create_issue_modules` 支持批量绑定） |
| 典型跨度 | 1～4 周 | 1～3 个月 |

一个工作项**同时**属于「本周期」和「登录模块」，这才是正确用法。只用一个维度，Plane 就退化成了普通待办列表。

> 注意这里的不对称性：**周期是互斥的**（代码中把工作项加入新周期时执行的是 `cycle_id` 的 `bulk_update`，而非新增记录），**模块是多对多的**（一个工作项可以同时属于「登录模块」和「安全加固模块」）。这个设计是合理的——一件事只能在一个时间盒里做，但它可以同时服务于多个交付目标。

## 二、开局：项目初始化清单

按顺序做完这 8 步，后面才不会返工。**加粗项是最容易被跳过、后期代价最大的。**

### 1. 定 Project Identifier（不可轻易改）
项目标识符会成为所有工作项编号的前缀（如 `WEB-142`）。规则：
- 2～5 个字符，全大写，团队口头能念出来
- 不能含 `& + , : ; $ ^ } { * = ? @ # | ' < > . ( ) % ! -` 等字符（代码中有正则校验）
- 一个 Workspace 内唯一

### 2. **设计状态流（States）—— 这是最重要的一步**

Plane 的状态归属 6 个**状态组**，所有统计、燃尽图、进度条都基于状态组而非状态名：

| 状态组 | 语义 | 建议自定义状态 |
| --- | --- | --- |
| `Triage` | 待分诊（未确认是否要做） | Triage |
| `Backlog` | 已确认要做，未排期 | Backlog |
| `Unstarted` | 已排期，未开工 | Todo、Ready |
| `Started` | 进行中 | In Progress、In Review、Testing |
| `Completed` | 完成 | Done、Released |
| `Cancelled` | 不做了 | Cancelled、Won't Do |

**实践建议**：
- 自定义状态可以有多个，但**必须归到正确的状态组**。把 "In Review" 错放进 `Completed` 组，燃尽图立刻失真。
- 状态数量控制在 5～7 个。每多一个状态，就多一次拖拽和一次心智负担。
- 设置项目 `default_state`，新建工作项自动落位。

### 3. 决定启用哪些功能开关
项目设置 → Features，逐项判断。**默认全关，按需开启**：

| 功能 | 什么时候开 | 什么时候别开 |
| --- | --- | --- |
| Cycles | 团队有固定迭代节奏 | 纯需求驱动、无节奏的支持型团队 |
| Modules | 项目跨度 > 1 个月，有多个交付物 | 短期一次性项目 |
| Views | 团队 > 5 人，需要不同视角 | 小团队用默认筛选即可 |
| Pages | 需要沉淀文档 / 会议纪要 / 方案 | 已有独立 Wiki 且不打算迁移 |
| Intake | 有外部提需求的渠道 | 需求全部来自团队内部 |
| Time Tracking | 需要工时统计 / 对外计费 | 内部团队，徒增录入负担 |
| Issue Types | 需要区分 Bug / Feature / Task 并分别统计 | 用标签就够了 |

### 4. 建标签体系（Labels）
标签支持父子分组，**用前缀命名法**避免标签爆炸：

```
type/bug        type/feature      type/tech-debt
area/frontend   area/backend      area/infra
flag/blocked    flag/needs-design flag/customer-reported
```

原则：标签用于**横切关注点**（跨模块、跨周期的属性）。凡是能用状态、模块、周期表达的，就不要做成标签。

### 5. 配置估点（Estimates）
两种类型二选一：

- **Categories（类别）**：`XS / S / M / L / XL` —— 适合刚开始做估算的团队，认知负担低
- **Points（点数）**：`1 / 2 / 3 / 5 / 8 / 13` —— 斐波那契数列，适合成熟团队，可做速率（Velocity）计算

**建议**：新团队从 Categories 起步，跑 3～4 个周期建立基线后再切 Points。估点的价值不在精确，而在**暴露认知分歧**——两个人估出 S 和 XL，说明对需求理解不一致，这个讨论比数字本身值钱。

### 6. 设置自动化（Automations）
项目设置 → Automations，两个规则：
- **Auto-archive**：N 个月（1～12）无更新的已完成工作项自动归档 → 建议 1～2 个月
- **Auto-close**：N 个月无活动的工作项自动关闭 → 建议 3 个月，用于清理僵尸需求

这两条能让 Backlog 保持健康，不设置的话半年后 Backlog 会变成垃圾场。

### 7. 邀请成员并分配角色

| 角色 | 权限边界 | 适用 |
| --- | --- | --- |
| **Admin (20)** | 全部，含项目设置、成员管理、删除项目 | 项目负责人、团队 Leader |
| **Member (15)** | 创建/编辑工作项、周期、模块、页面 | 开发、设计、测试 |
| **Guest (5)** | 受限只读（可通过 `guest_view_all_features` 放宽） | 外部协作方、客户、跨部门观察者 |

**注意**：Guest 默认看不到全部功能。若需要外部方参与但不想给 Member 权限，开启项目的 `guest_view_all_features`，或改用**公开发布（Deploy Board）**。

### 8. 设置项目可见性
- **Public**：工作区内所有人可见 → 默认选这个，透明度优先
- **Secret**：仅项目成员可见 → 仅用于薪酬、法务、并购等敏感项目

## 三、两种主流工作法的落地方案

### 方案 A：Scrum / 固定迭代（推荐给产研团队）

**配置**
- 开启 Cycles + Modules + Views
- 估点用 Points
- 默认布局：Backlog 用 List，迭代内用 Kanban

**节奏**

| 时点 | 动作 | 用到的功能 |
| --- | --- | --- |
| 迭代开始前 1～2 天 | **迭代规划会**：从 Backlog 挑选工作项拖入新 Cycle，逐项估点、指派 | Cycles、Estimates、批量拖拽 |
| 每日 | **站会**：打开 Cycle 的 Kanban，从右往左过一遍（先看接近完成的） | Kanban 布局、`flag/blocked` 标签 |
| 迭代中 | 新需求默认进 Backlog，**不进当前 Cycle**；紧急插入必须显式移除等量工作 | Backlog、估点做置换依据 |
| 迭代结束 | **评审 + 回顾**：看燃尽图、完成率、未完成项迁移 | 燃尽图、`progress_snapshot` |

**关键纪律**
- Cycle 一旦开始，范围锁定。Plane 会在周期结束时冻结 `progress_snapshot`，如果中途随意增删，这份快照就失去回顾价值。
- 未完成的工作项**不要**直接顺延——重新评估是否还需要做，很多需求过一个迭代就不重要了。

### 方案 B：Kanban / 持续流（推荐给支持、运维、平台团队）

**配置**
- 关闭 Cycles，开启 Modules + Intake
- 不用估点，改用**在制品限制（WIP Limit）**——Plane 没有内置 WIP 限制，用 Kanban 列的卡片数手动约束
- 默认布局：Kanban

**节奏**

| 时点 | 动作 |
| --- | --- |
| 需求进来 | 统一进 **Intake**，不直接建工作项 |
| 每日/隔日 | **分诊会**：Intake 队列逐条处理 —— Accept（接受并排期）/ Reject（拒绝）/ Snooze（延后到指定日期）/ Duplicate（标记重复） |
| 持续 | 看板从左往右流动，**关注停留时长**而非完成数量 |
| 每周 | 看 Analytics 的 Created vs Resolved 面积图，两条线是否收敛 |

**关键纪律**
- Intake 队列必须**每天清空**。积压的分诊队列比积压的 Backlog 更有害——提需求的人得不到反馈。
- Snooze 要设明确日期，不要无限期延后。

## 四、五种布局分别在什么场景用

选错布局会让同样的数据变得难以决策。

| 布局 | 最佳场景 | group_by 建议 | 别用它做什么 |
| --- | --- | --- | --- |
| **List** | Backlog 梳理、批量整理、快速扫读 | Priority 或 Module | 不适合看进度流动 |
| **Kanban** | 日常执行、站会、状态推进 | State（默认） | 超过 50 张卡就会失控，先筛选再看 |
| **Spreadsheet** | 批量编辑属性、导出前核对、数据密集型审查 | 不分组 | 不适合日常执行 |
| **Calendar** | 截止日期密集的运营 / 内容 / 市场类工作 | — | 不适合无明确日期的开发任务 |
| **Gantt** | 排期规划、依赖梳理、给管理层汇报 | — | 不适合日常执行，维护成本高 |

**Gantt 的专属价值**：它是唯一支持**依赖关系**的布局（`enableDependency`）。当你需要回答"如果 A 延期，B 会不会受影响"时，只有甘特图能给答案。缩放支持周 / 月 / 季三档。

**保存视图的正确姿势**——为每个高频问题存一个视图：

| 视图名 | 筛选条件 | 谁在用 |
| --- | --- | --- |
| 我的本周 | assignee=我 AND target_date≤本周末 | 每个人 |
| 阻塞项 | label=flag/blocked OR 有 blocked_by 关系 | 每日站会 |
| 无人认领 | assignee 为空 AND state_group=Unstarted | 团队 Leader |
| 逾期未完成 | target_date<今天 AND state_group≠Completed | 项目负责人 |
| 本迭代 Bug | cycle=当前 AND type=Bug | 测试 / QA |

工作区级视图（Workspace Views）可跨项目筛选，适合管理多个项目的负责人。

## 五、把数据用起来：看哪些指标、怎么看

### 5.1 三个必看的图

**1. 燃尽图（Cycle / Module 侧边栏）**

蓝色实线是实际剩余，灰色虚线是理想匀速线。读法：

| 形态 | 含义 | 该做什么 |
| --- | --- | --- |
| 实线长期在虚线**上方** | 进度落后 | 立即砍范围，别指望最后冲刺 |
| 实线**平台期**后陡降 | 全部堆到最后完成（典型的"最后一天全部 Done"） | 检查是否状态更新不及时，或任务拆得太粗 |
| 实线**阶梯状**均匀下降 | 健康 | 保持 |
| 实线**向上跳** | 迭代中途加需求 | 检查范围管理纪律 |

**2. Created vs Resolved（分析 → 工作项）**

两条面积曲线：创建量 vs 解决量。这是**团队可持续性**的核心指标。
- 创建 > 解决 且持续 3 个周期以上 → 团队超载，Backlog 会无限膨胀，必须扩容或砍需求
- 解决 > 创建 → 有余量，可以承接更多或投入技术债
- 两线贴合 → 稳态

**3. 优先级分布（分析 / 成员资料页）**

如果 Urgent + High 占比 > 40%，说明**优先级已经失效**——所有事情都紧急等于没有紧急。这时该做的是重新定级，而不是催进度。

### 5.2 自定义分析：16 × 9 的组合空间

分析页支持自由组合 X 轴（16 种维度）× Y 轴（9 种指标）× group_by（二次分组）。几个高价值组合：

| X 轴 | Y 轴 | group_by | 回答什么问题 |
| --- | --- | --- | --- |
| `ASSIGNEES` | `IN_PROGRESS_WORK_ITEM_COUNT` | — | **谁手上并行任务过多？**（单人 > 3 个进行中就该干预） |
| `ASSIGNEES` | `ESTIMATE_POINT_COUNT` | `STATE_GROUPS` | 负载是否均衡 |
| `LABELS` | `WORK_ITEM_COUNT` | `STATE_GROUPS` | 哪个领域积压最重 |
| `COMPLETED_AT`（按 WEEK 聚合） | `ESTIMATE_POINT_COUNT` | — | **团队速率曲线**，用于预测 |
| `PRIORITY` | `BLOCKED_WORK_ITEM_COUNT` | — | 高优先级的事情是不是被卡住了 |
| `MODULES` | `PENDING_WORK_ITEM_COUNT` | `PRIORITY` | 哪个模块离交付最远 |
| `CREATED_AT`（按 MONTH 聚合） | `WORK_ITEM_COUNT` | `WORK_ITEM_TYPES` | 需求 / Bug 的长期结构变化 |

时间维度（START_DATE / TARGET_DATE / CREATED_AT / COMPLETED_AT）支持 **DAY / WEEK / MONTH / YEAR** 四档聚合粒度。时间范围可选昨天 / 近 7 天 / 近 30 天 / 近 3 个月。

配色可在 Modern / Horizon / Earthen 三套调色板间切换，自动适配亮暗主题。

### 5.3 一个容易忽略的入口：成员资料页

`/:workspaceSlug/profile/:userId` 提供单人视角的优先级分布（柱状图）、状态分布（饼图）、工作负载和活动流。**1:1 沟通前先看这一页**，比问"你最近忙什么"高效得多。

## 六、协作规范建议

### 工作项的最小可执行标准
一个工作项在被拖入 Cycle 前，必须满足：
1. 标题是**动宾结构**（"修复登录页 Safari 白屏"，而非"登录问题"）
2. 有指派人
3. 有估点
4. 描述里写清**验收标准**（用编辑器的任务列表写 checklist）
5. 归属一个 Module

不满足就留在 Backlog。这条纪律能消除 80% 的"这个任务到底要做什么"的往返沟通。

### 用好关系（Relations）而不是标签
Plane 支持 `blocking` / `blocked_by` / `duplicate` / `relates_to` 四类关系。
- 依赖用 **blocked_by**，不要用标签 `flag/blocked` —— 前者能在甘特图上可视化，后者不能
- 标签只用于**没有明确对象**的状态标记

### 子工作项 vs 模块
- 拆分后**仍由同一人在同一周期内完成** → 用子工作项（Sub-issues）
- 拆分后**由不同人跨周期完成** → 用模块（Module）

由于工作项与模块是多对多关系，可以善用这一点做**双重归属**：一个工作项既属于「支付重构」（业务模块），又属于「Q3 技术债清理」（治理模块），两个模块的进度条会各自正确统计。但别滥用——超过 2 个模块归属就说明模块划分本身有问题。

### 评论的内外部区分
`IssueComment` 支持 `INTERNAL` / `EXTERNAL` 两种可见性。在公开发布（Deploy Board）的项目里，内部讨论标 INTERNAL，对外回复标 EXTERNAL——这样可以在同一个工作项里同时做内部协作和客户沟通。

### 页面（Pages）的用法分层

| 类型 | 放什么 | 访问级别 |
| --- | --- | --- |
| 工作区级页面（`is_global`） | 团队规范、术语表、Onboarding 文档 | Public |
| 项目级页面 | PRD、技术方案、会议纪要 | Public |
| 个人页面 | 草稿、个人笔记 | Private |

页面支持**嵌套**（父子树）、**版本历史**、**多人实时协同**（Yjs），并可用 `/` 斜杠命令内嵌工作项——PRD 里直接嵌入相关工作项，状态实时同步，不用手动更新链接。

### 便签（Stickies）
工作区级的临时笔记板，适合放"待办速记""临时链接""本周关注点"。不要拿它当任务系统——它没有状态、指派人和截止日期。

## 七、对外协作：公开发布的三种玩法

`DeployBoard` 支持把 7 类实体（项目 / 工作项 / 模块 / 周期 / 页面 / 视图 / Intake）发布到公网，由 `apps/space` 承载，访问者无需账号。

| 玩法 | 发布对象 | 开启的互动 | 场景 |
| --- | --- | --- | --- |
| **公开路线图** | 项目 或 视图（筛选 = 已规划的功能） | 关闭评论、**开启投票** | 让用户投票决定优先级 |
| **公开反馈渠道** | Intake | 开启评论 | 收集外部 Bug / 需求，进入分诊队列 |
| **对客交付看板** | 项目 或 周期 | 开启评论 + 活动流 | 让客户实时看到进度，减少汇报 |

四个开关独立可控：评论、表情回应、投票、活动流。随时可 `is_disabled` 关闭。

## 八、自动化与集成

### Webhook（免费版可用）
可订阅 5 类事件：`project` / `issue` / `module` / `cycle` / `issue_comment`。支持工作区级与项目级，带调用日志（`WebhookLog`）。

典型用法：
- 工作项进入 `Completed` → 推送到企业微信 / 飞书群
- 高优先级 Bug 创建 → 触发值班告警
- 周期结束 → 自动生成周报

### 公开 REST API
`apps/api/plane/api/` 提供完整的 REST 接口（project、work_item、cycle、module、state、label、member、intake、estimate、sticky、asset、invite、user）并附 OpenAPI schema。在个人设置里生成 API Token 即可调用。

配合 `external_source` / `external_id` 字段，可以做**双向同步**——从 Jira / GitHub Issues 导入时保留原系统 ID，后续增量同步不会重复创建。

### 导出
- 工作项：JSON / CSV / XLSX
- 页面：PDF
- 分析数据：通过 `ExportAnalyticsEndpoint`

## 九、常见反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一个 Workspace 只建一个 Project，所有事情堆里面 | 筛选失效、权限无法隔离、分析无意义 | 按团队 / 产品线拆项目 |
| 建了几十个 Project，每个只有几个工作项 | 上下文碎片化、成员疲于切换 | 用 Module 代替小项目 |
| 只用 Cycle 不用 Module | 无法回答"这个功能做完了吗" | 补上范围维度 |
| 只用 Module 不用 Cycle | 没有节奏，无法预测交付时间 | 补上时间维度 |
| 自定义状态归错状态组 | 燃尽图、进度条、所有统计全部失真 | 建状态时确认状态组 |
| Backlog 无限增长，从不清理 | 变成垃圾场，没人愿意打开 | 开启 Auto-archive / Auto-close |
| 迭代中途随意增删工作项 | `progress_snapshot` 失去回顾价值，速率无法计算 | 范围锁定，紧急插入必须等量置换 |
| 标签超过 30 个且无命名规范 | 没人记得该用哪个，筛选无效 | 前缀命名法 + 定期合并 |
| 所有工作项都是 Urgent / High | 优先级失效 | 强制配额：Urgent ≤ 5%，High ≤ 20% |
| 用工作项描述当文档 | 内容散落、无法检索、无版本 | 长内容放 Pages，工作项里内链 |
| Intake 队列长期积压 | 提需求的人得不到反馈，绕过流程 | 每日清空分诊队列 |
| 开启 Time Tracking 但没人录入 | 数据不完整，比没有更糟 | 要么强制执行，要么关掉 |
