# ADR-0001 · 本体先行（Ontology First）

| 项 | 值 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-08-03 |
| 决策者 | 架构组 |
| 关联需求 | FR-ONT-001 ~ FR-ONT-012 |

## 背景

传统研发管理工具中，需求是文档、架构是图片、知识是 Wiki 页面。
这些形态对人可读，对机器不可理解——AI 只能做字符串层面的摘要与检索，
无法回答"这个故障对应哪个需求、当时为什么这么决定"。

同时，若允许各模块自行定义数据结构，系统会迅速退化为一堆彼此不认识的表，
关联只能靠人工挂链接，链接必然腐化。

## 决策

**所有业务对象先在 Ontology Registry 中定义本体，再派生存储、API 与 UI。**

```
Ontology → Storage Schema → API → UI
```

具体约束：

1. 新增任何领域对象，必须先注册 EntityType（含属性与关系定义）。
2. 数据库结构由本体派生或校验，禁止绕过本体私建业务表。
3. API 暴露的字段语义必须存在于本体中。
4. UI 是本体的渲染视图，不得在 UI 层定义业务语义。
5. 关系是一等公民：有类型、方向、逆关系、属性与来源。
6. 本体版本化（SemVer），破坏性变更需独立 ADR 与迁移方案。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| A. 传统 Schema First（各模块自定义表） | 起步快，团队熟悉 | 语义割裂，关联靠人工，AI 无法推理 | 与产品愿景直接冲突 |
| B. 采用 RDF/OWL 标准本体 | 生态成熟，推理能力强 | 学习成本高，与关系库/业务代码阻抗大，性能不可控 | 团队与场景不匹配；保留导出 RDF 的能力作为折中 |
| C. 文档数据库 + 弱 Schema | 灵活 | 无约束即无语义，问题被推迟而非解决 | 无法保证一致性与可推理性 |

## 后果

### 正面

- AI 可沿关系推理，而非做相似度猜测
- 全链路追溯（Requirement → Release → Knowledge）成为系统固有能力，而非附加功能
- 新增对象类型无需新增专用 API（配合 ADR-0002）
- 影响面分析、知识关联、自动关系建立都有统一基础

### 负面 / 代价

- 前期投入大：本体设计先于任何业务功能，M0 交付看起来"没有可见功能"
- 团队需要学习本体建模，存在上手成本
- 本体变更有流程约束，短期灵活性降低

### 需要后续处理

- [ ] 提供默认本体包，降低上手门槛（Q-A3 相关）
- [ ] 提供本体可视化浏览器（FR-ONT-012）
- [ ] 建立本体评审机制，避免本体膨胀

## 验证方式

- CI 检查：不存在未在 Ontology Registry 注册的业务表
- 自动化测试：违反本体约束的写入被拒绝并返回字段级错误
- 每日巡检：孤儿对象与断链报告（FR-ONT-010）
