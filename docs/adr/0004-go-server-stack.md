## 背景

M0 的全部开发工作被服务端语言选型阻塞。候选为 TypeScript/Node 与 Go。

ProjectOS 的服务端负载有三个特征：

1. **高并发 I/O**：大量并行的 Connector 调用、Agent Run、事件消费
2. **长时任务**：Agent Run 可持续数分钟，需要稳定的取消、超时与背压控制
3. **强类型领域模型**：DDD 聚合与不变量需要编译期保障

## 决策

**服务端采用 Go（1.22+）。**

配套约定：

| 项 | 选择 |
| --- | --- |
| HTTP 框架 | 标准库 `net/http` + 轻量路由；不引入重量级框架 |
| API 规范 | OpenAPI 3.1 为写侧真源，代码由规范生成 |
| 数据库访问 | `pgx` + `sqlc`（编译期校验 SQL），不使用重 ORM |
| 项目结构 | 按限界上下文分模块（`internal/<bc>/`），domain 层无框架依赖 |
| 依赖方向校验 | CI 中以静态分析强制（对应 FR-ARCH-001） |
| 并发模型 | goroutine + `context.Context` 贯穿；Agent Run 全链路可取消 |
| 可观测 | OpenTelemetry（trace/metric/log 统一） |

Go 不适用的部分：

- 前端与本体驱动渲染层：TypeScript
- 数据处理 / 评估脚本：Python（离线，不进入服务端主链路）

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
| --- | --- | --- | --- |
| TypeScript / Node | 前后端同语言；LLM 生态库最丰富；迭代快 | 长时任务与高并发下内存与背压控制较弱；类型系统运行期无保障 | 与长时 Agent Run 的运维特征不匹配 |
| **Go** | 并发模型契合；部署为单二进制；运行期资源可预测；强类型 | LLM 生态库不如 Python/TS 成熟；泛型表达力有限，领域建模略啰嗦 | **已选** |
| Java / Kotlin | DDD 生态成熟；企业级中间件齐全 | 启动与内存开销大；迭代速度慢 | 团队与阶段不匹配 |
| Rust | 性能与安全最强 | 开发速度慢，招聘面窄 | 早期阶段代价过高 |

## 后果

### 正面

- Agent Runtime 的并发调度、超时、取消、背压有语言级支持
- 单二进制部署，运维简单，容器镜像小
- 编译期类型检查覆盖领域不变量的相当一部分
- 运行期资源占用可预测，成本模型清晰

### 负面 / 代价

- LLM / Agent 相关 SDK 在 Go 生态中较薄，部分能力需自行封装（尤其是 MCP 客户端、流式解析、token 计数）
- 泛型表达力有限，统一 Resource 模型（ADR-0002）的通用 CRUD 会有一定样板代码
- 前后端不同语言，本体元数据需要跨语言共享 —— 以 OpenAPI + JSON Schema 作为契约真源解决
- 团队若不熟悉 Go，前两个迭代速度会下降

### 需要后续处理

- [ ] 封装 Go 版 MCP 客户端（FR-CON-008 前置）

- [ ] 建立 Go 代码规范与领域层样板生成工具，降低 ADR-0002 的样板成本
